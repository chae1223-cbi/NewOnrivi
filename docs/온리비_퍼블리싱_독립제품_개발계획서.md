# 온리비 퍼블리싱 독립 제품 개발 계획서

버전 5.0 · 2026-11-20 · 구현 전 계획

## 1. 제품 결정

**Onrivi Author는 범용 문서 편집 제품으로 유지한다. Onrivi Publishing은 같은 Markdown 원고를 사용해 전자책과 종이책을 제작하는 독립 제품으로 개발한다.** 두 제품은 검증된 편집·문서 처리 기능만 공통 모듈로 공유한다. Author에 출판 메뉴와 검증 런타임을 추가하지 않는다.

첫 출시는 **Windows용 Publishing과 가변형 EPUB**에 집중한다. 인쇄소 제출용 PDF와 고정형 EPUB은 별도 출시 단계로 둔다. 기존 Author의 일반 EPUB·PDF 내보내기는 그대로 유지하며, Publishing 출력의 품질 기준과 혼동하지 않는다.

| 제품 | 책임 | 배포 |
| --- | --- | --- |
| Onrivi Author | 일반 Markdown 작성, 기존 서식·파일 관리·일반 내보내기 | 기존 웹·데스크톱 유지 |
| 공통 Core | 검증된 Markdown·파일·이미지·서식·편집 기능의 최소 공유부 | 사용자에게 별도 설치 요구 없음 |
| Onrivi Publishing | 도서 프로젝트·구성·조판·검사·출판 파일 생성 | 독립 Windows 앱 우선 |

Publishing은 ISBN 발급, 판매처 등록, DRM, 인쇄 주문을 대행하지 않는다. 원고와 이미지를 출판 전용 서버에 저장하지 않고 로컬에서 제작한다. 다만 계정·라이선스 확인은 기존 인프라와의 연결 정책을 따로 검증한다.

## 2. 현재 코드 기준선과 재사용 판단

현재 저장소는 Author용 단일 Electron 앱이다. `package.json`에는 Author 앱 ID, 설치·업데이트 설정이 있고 `main.js`에는 Author 전용 프로토콜, 사용자 설정 경로, 라이선스·파일 IPC가 있다. Publishing을 독립 설치하려면 앱 ID뿐 아니라 이 경계 전체를 분리해야 한다.

| 현재 구성 | 재사용 가능성 | 먼저 확인할 조건 |
| --- | --- | --- |
| `frontend/src/lib/epubGenerator.ts` | EPUB 패키지, 섹션, 목차, 이미지 처리의 출발점 | 실제 출력 EPUB의 검증 결과, 다중 원고·도서 정보·내부 링크 |
| `frontend/src/lib/export/pdfExporter.ts`, `paginatedPrint.ts` | 일반 PDF 및 페이지 계산의 출발점 | 장 시작면·홀짝 여백·목차 쪽수·폰트·인쇄 사양 |
| `VisualDocumentEditor`, Markdown 렌더러 | 원고 편집 화면에 활용 | 앱 상태·브라우저 API·Electron IPC 의존성 분리 비용 |
| 서식 프로필, 이미지·로컬 파일 처리 | 책 본문 서식과 리소스 연결에 활용 | 프로젝트 이동 시 상대경로·폰트·이미지 재현성 |
| `:::scene` 그림책 모델 | 후속 고정형 EPUB·펼침면의 후보 | 장면과 실제 물리 페이지의 매핑 |
| 기존 라이선스·설치 경로 | 인증 흐름 일부 활용 | Publishing 권한, 오프라인 사용, 별도 사용자 데이터·업데이트 |

**재사용은 코드 존재가 아니라 결과물 검증으로 결정한다.** 기존 EPUB과 PDF가 생성되는 사실만으로 공식 EPUB 검사 통과나 인쇄소 제출 적합성을 보장하지 않는다. 공통화도 실제로 두 제품이 사용하는 부분부터 진행한다.

## 3. 개발 순서와 출시 경계

```text
0. 기존 출력 감사·기준 도서 선정
   ↓
1. Publishing 독립 앱 셸 + 최소 공통 모듈 + 도서 프로젝트
   ↓
2. 가변형 EPUB 생성·검사 → Publishing 첫 출시
   ↓
3. 인쇄용 내지·표지 PDF → 종이책 기능 출시
   ↓
4. 고정형 EPUB·그림책·사진집 → 후속 출시
   ↓
5. 웹 로컬 모드 → 파일 접근·출력 호환성 확인 후 제공
```

각 단계는 **작동하는 결과물과 Author 회귀 검사**를 통과한 뒤 다음 단계로 넘어간다. 일정은 0단계 감사 후 산정한다. 기존 제안서의 주 단위 추정은 독립 설치, 제품별 라이선스, Core 추출 및 검증 비용이 반영되기 전이므로 확정 일정으로 사용하지 않는다.

## 4. 단계 0: 기준 도서로 기존 기능 감사

새 제품 코드를 분리하기 전에 실제 원고로 현재 Author 출력 품질을 측정한다.

### 감사 자료

1. 일반 에세이: 장 제목, 간단한 이미지, 목차, 각주.
2. 이미지 중심 여행서: 여러 원고 파일, 한글 파일명, 이미지와 내부 링크.
3. 그림책 또는 사진집: `:::scene`, 고정 페이지 이미지, 짧은 설명.
4. 기술서 샘플: 표, 코드, 수식, Mermaid, 참고문헌.

### 산출물

- 기존 EPUB의 압축 구조, 메타데이터, 목차, 링크, 이미지·폰트 포함 상태와 검사 결과.
- 대표 EPUB 독서기에서의 화면·이동·각주·이미지 동작 기록.
- 기존 PDF의 실제 페이지 크기, 여백, 페이지 번호, 페이지 분할, 폰트 포함 상태와 이미지 해상도 기록.
- 모듈별 브라우저·Electron·서버 의존성 지도와 최소 추출 목록.
- Author 기존 출력의 회귀 비교용 샘플 파일과 검사 절차.

이 결과가 1차 제품의 작업 목록·공수·지원 형식을 결정한다. 원고별 문제가 발견되면 재사용 가능 기능과 새로 만들 기능을 분리해 기록한다.

## 5. 제품 아키텍처

### 5.1 책임 경계

Core는 도서·출판사·판매처·제품 요금제를 알지 않는다. Publishing은 Author 화면이나 내부 상태를 직접 import하지 않는다. Author는 Publishing 없이 단독 빌드·실행되고, Publishing은 Author 설치 없이 단독 실행된다.

| 소유 영역 | 주요 기능 |
| --- | --- |
| 최소 Core | Markdown 파싱·직렬화, 파일·이미지 경로 해석, 서식 데이터, 공유 가능한 에디터·렌더링 구성 요소 |
| Author | 기존 범용 편집 흐름, 웹·클라우드 기능, 일반 출력 |
| Publishing | 도서 프로젝트, 출판 구성, 메타데이터, 간지, 판권지, 형식별 조판, 검증, 파일 생성 |

처음부터 `packages/markdown`, `packages/editor`, `packages/renderer` 전체를 이동하는 대규모 리팩터링은 개발의 전제 조건으로 삼지 않는다. 먼저 순수 함수와 타입, 파일 입출력 인터페이스를 추출하고 Publishing이 실제로 재사용할 때 UI 구성 요소를 분리한다. 두 제품에서 소스 코드를 복사해 장기 유지하지 않는다.

### 5.2 저장소와 배포

동일 Git 저장소 안의 독립 앱과 버전 관리된 공통 패키지를 우선 검토한다. 별도 Git 저장소는 배포·협업상 실제 이점이 확인될 때 결정한다. Publishing의 앱 ID, 실행 파일명, 설치 위치, 사용자 설정·캐시·로그, 딥링크, 업데이트 채널을 Author와 분리한다. `.md` 파일 연결의 기본 앱을 두 설치 프로그램이 서로 빼앗지 않도록 선택 정책을 둔다.

공통 모듈을 변경하면 두 앱의 빌드·회귀 검사를 수행하되 출시는 제품별로 결정한다. EPUB 검증기나 인쇄 도구는 Author 번들에 포함하지 않는다.

## 6. 도서 프로젝트와 원고

**원고 하나**는 반드시 Markdown 파일 하나라는 뜻이 아니다. 하나의 도서는 단일 파일 또는 순서가 있는 여러 Markdown 파일로 구성된다. 원고 원본을 복제·변환하지 않고 `book.json`이 연결 관계와 도서 정보를 가진다.

```text
사용자 지정 도서 폴더/
  book.json
  manuscripts/
    00-prologue.md
    01-chapter.md
  images/
  output/
```

`book.json`의 최소 정보는 스키마 버전, 프로젝트 ID, 도서 메타데이터, 순서가 있는 구성 항목, 형식별 출력 프로필, 설정 수정 버전이다. 구성 항목은 고유 ID와 유형, 원고 상대경로 또는 생성 요소 정보를 가진다. 제목·저자·언어·전자책 식별자 등 출력에 필요한 값을 입력·검증한다. ISBN은 사용자가 보유할 때만 설정한다.

원고 경로는 프로젝트 기준 상대경로를 우선한다. 외부 폴더의 원고나 이미지를 연결하려면 접근 권한, 이동 가능성, 내보내기 시 포함 정책을 명시한다. 폴더가 이동돼도 상대경로 자료는 다시 열려야 한다. 프로젝트 설정과 원고 저장은 충돌 감지와 안전한 파일 교체를 적용하며, 동일 파일을 두 제품에서 동시에 수정하면 이전 내용을 자동 덮어쓰지 않는다.

## 7. 도서 구성과 편집 화면

### 7.1 구성 패널

Publishing은 구성 항목 추가·제외·순서 이동·제목 변경·파일 연결을 제공한다. 기본 항목은 표지, 속표지, 판권지, 머리말, 부·장, 간지, 본문, 부록, 저자 소개다. EPUB과 인쇄 PDF는 같은 순서의 구성 모델을 사용하지만 실제 출력은 별도 엔진이 처리한다.

속표지·판권지·목차는 입력 정보에서 초안을 생성하고 사용자가 수정할 수 있다. 자동 생성 내용과 수동 수정 내용의 우선순위를 명확히 저장해 다음 생성 때 사용자의 수정이 사라지지 않게 한다.

### 7.2 간지

간지는 독립된 출판 구성 항목이다. 별도 Markdown 파일 연결을 우선 지원하고, `:::divider` 같은 인라인 문법은 기존 파서와 저장·재열기 호환성이 확인된 뒤 선택적으로 도입한다. EPUB 가변형에서는 독립 섹션으로, 인쇄 PDF에서는 독립 페이지로 출력한다. 홀수 쪽 시작과 빈 쪽 삽입 여부는 인쇄 프로필에서 정한다.

### 7.3 화면

Publishing 앱은 프로젝트 시작, 구성, 원고 편집, 도서 정보, 서식, 미리보기, 검사, 출력 화면을 제공한다. 초기 버전은 기존 Markdown 에디터와 렌더러를 활용하되 Publishing의 화면 흐름을 Author와 분리한다. EPUB 미리보기는 기기·독서기별 재배치 차이를 전제로 하고, 인쇄 미리보기는 최종 PDF의 실제 판형·페이지 번호와 일치해야 한다.

## 8. 가변형 EPUB: 첫 출시 기능

### 8.1 출력 범위

기존 EPUB 생성기의 패키징·목차·섹션 분할을 감사 결과에 따라 재사용한다. 도서 프로젝트의 구성 순서대로 XHTML, 이미지, CSS, 내비게이션, 패키지 메타데이터를 생성한다. 내부 링크는 원고 파일과 장 제목이 중복되어도 안정적으로 연결되는 식별자를 사용한다. 원격 이미지나 실행 스크립트에 의존하지 않으며 필요한 리소스를 결과물에 포함한다.

표, 코드, 체크리스트, 각주, 참고문헌, 수식, Mermaid는 대표 샘플의 실제 결과에 따라 지원 범위를 명시한다. 수식·도표는 EPUB 독서기 호환성을 확인한 표현으로 변환하고, 이미지 대체 설명과 언어·제목 계층을 점검한다. 한 형식에서 표현할 수 없는 요소는 조용히 삭제하지 않고 검사 결과에 표시한다.

### 8.2 검사와 완료 기준

내부 사전 검사는 누락 파일·이미지, 잘못된 링크, 필수 메타데이터, 제목 구조, 과도한 리소스 크기를 잡는다. Windows에서는 고정 버전의 EPUBCheck 실행 가능성을 확인하고 사용자가 실행 결과를 볼 수 있게 한다. Java 런타임 포함·별도 설치·업데이트 방식은 감사 단계에서 결정한다.

첫 출시 기준은 **선정한 기준 도서 EPUB의 검사 오류 0건**, 경고 검토, 내부 링크·이미지 정상, 대표 독서기에서 열림, Author 일반 EPUB 출력 회귀 없음이다. 이 결과가 모든 판매처의 승인까지 보장하는 것은 아니다.

## 9. 인쇄용 PDF: 후속 출시 기능

일반 PDF 내보내기와 별도로, 인쇄소 제출을 위한 **내지 PDF**와 **전체 표지 PDF**를 생성한다. 내지는 판형, 내외측 여백, 제본 여유, 홀짝 페이지, 간지, 장 시작면, 빈 페이지, 쪽번호와 머리말·꼬리말을 관리한다. 목차 쪽수는 최종 조판 결과에서 생성하며, 목차 길이 변경이 본문 페이지를 밀면 다시 조판한다.

표·이미지·문단의 넘침, 고아줄·과부줄, 폰트 포함 상태를 검사한다. 표지는 앞표지·책등·뒤표지의 한 장 파일로 만들고, 책등 두께는 인쇄소·종이 사양에 따른 값 또는 사용자가 제공한 값으로 설정한다. 재단 여유, 이미지 해상도, 색상 프로파일, PDF/X 등은 인쇄소별 출력 프로필과 실제 생성 파일에서 검증한다. 현재 PDF 엔진이 요구 사양을 만족하지 못하면 변환 엔진을 별도 평가한다.

출시 기준은 페이지 수·판형·홀짝 여백·쪽번호·목차의 일치, 폰트와 이미지 검사, 선정한 인쇄소 사양 확인, 시험 인쇄 결과다. 실제 인쇄소 승인 여부는 해당 인쇄소가 판단한다.

## 10. 고정형 EPUB과 이미지·글 펼침면: 후속 출시 기능

기존 `:::scene` 장면과 그림책 페이지 모델을 검토한다. 고정형 EPUB은 페이지별 XHTML, 고정 viewport, 읽는 순서, 좌우 펼침면 정보와 리소스를 관리한다. 단순 PDF 페이지 이미지 변환을 기본 구조로 삼지 않는다.

[왼쪽 이미지·오른쪽 설명 펼침면 계획](단행본_좌측이미지_우측설명_펼침면_편집기_구현계획서.md)은 **Publishing 소유의 후속 편집·인쇄 기능**으로 옮긴다. 화면의 한 펼침면은 실제 이미지 왼쪽 한 쪽과 글 오른쪽 한 쪽이며, PDF에는 각각 독립 페이지로 출력한다. 오른쪽 글 넘침과 표지·빈 쪽에 따른 홀짝 순서를 별도 검증한다. Author에 새 출판 모드로 추가하지 않는다.

## 11. 라이선스, 파일 안전, 오프라인

Author 기존 구매·사용 권리는 유지한다. Publishing은 별도 제품 권한을 도입하되 Author 플랜 포함, 별도 판매, 번들 중 가격 정책은 출력 품질과 비용 검증 후 결정한다. 공통 인증 인프라는 재사용하되 제품별 권한은 명확히 분리한다. 기존 오프라인 사용 정책을 조사해 Publishing의 실행·편집·출력에 같은 수준으로 적용할 수 있는지 확인한다. 신규 서버에 상시 접속해야만 출판 파일을 만들도록 설계하지 않는다.

사용자가 허용한 로컬 폴더만 읽고 쓴다. 프로젝트 내부 상대경로가 루트를 벗어나지 않는지, 심볼릭 링크·정션이 경계를 넘지 않는지 검사한다. EPUB XHTML의 스크립트와 위험한 외부 리소스를 제거한다. 원고·설정·출력은 임시 파일을 활용한 안전한 저장과 충돌 감지를 적용한다. 검사기 실행 시간·입력 크기와 출력 크기를 제한한다.

## 12. 웹 로컬 모드: Windows 출시 후

웹은 사용자가 브라우저에서 승인한 폴더만 열 수 있다. Windows 앱과 같은 `book.json`과 Markdown·이미지를 읽을 수 있게 파일 입출력 어댑터를 분리한다. 웹에서 검증기를 실행하거나 인쇄 PDF를 만든다고 먼저 약속하지 않는다. 실제 브라우저의 파일 권한, 메모리, 폰트, 출력 엔진 제약을 검증한 뒤 지원 기능을 표시한다. Windows 공식 검증을 거치지 않은 EPUB은 그 상태를 명확히 보여준다.

## 13. 단계별 작업과 통과 조건

| 단계 | 주요 작업 | 통과 조건 |
| --- | --- | --- |
| 0. 출력·코드 감사 | 기준 도서 제작, EPUB/PDF 검사, 모듈 의존성 지도 | 결함 목록·재사용 범위·1차 작업량 산정 |
| 1. 독립 제품 기반 | 앱 ID·설정·업데이트·권한 분리, 최소 Core, `book.json` | Author 없이 Publishing 실행, 두 제품의 설정 충돌 없음 |
| 2. 가변형 EPUB | 도서 구성·메타데이터·간지·표지·출력·검사 | 기준 도서 검사 오류 0, 대표 독서기 검증, Author 회귀 없음 |
| 3. 인쇄 PDF | 내지·표지, 홀짝면·목차·인쇄 프로필 | 실제 시험본과 선정 인쇄소 사양 검증 |
| 4. 고정형 EPUB | 장면·펼침면, 고정 viewport, 독서기 검사 | 대상 그림책·사진집이 목표 독서기에서 정상 작동 |
| 5. 웹 로컬 | 프로젝트 교차 열기, 지원 범위별 출력 | 원고 손실 없이 Windows·웹 왕복, 권한·출력 제한 표시 |

**1차 제품 출시는 0~2단계와 독립 설치·제품 권한·업데이트·회귀 검사 완료 시점**이다. 서식 상품이나 유료 제작 서비스는 제품 개발의 통과 조건에 넣지 않는다.

## 14. 인수 테스트와 출시 자료

- 에세이·여행서·기술서 EPUB에서 표지, 속표지, 판권지, 간지, 목차, 이미지·링크·각주와 본문 순서 확인.
- 한글·공백·특수문자 파일명, 중복 장 제목, 누락 이미지·링크, 원고 순서 변경·이동, 동시 수정 충돌 확인.
- 작업 중 강제 종료와 재실행 후 `book.json`·원고·출력 파일의 무결성 확인.
- 기존 Author의 일반 EPUB·PDF, 그림책, 라이선스, 설치·업데이트 결과 비교.
- 인쇄 단계에서 실제 PDF 페이지 크기·쪽수·홀짝면·책등 치수와 시험 인쇄물 확인.
- 고정형 단계에서 그림책과 왼쪽 이미지·오른쪽 글 펼침면의 읽는 순서 검증.

제품 출시 전에 개발자 자신의 원고로 실제 전자책을 만들어 검사하고 대표 독서기에서 읽는다. 인쇄 기능은 실제 시험 인쇄로 확인한다. 이 과정에서 얻은 파일, 검사 보고서, 오류 수정 기록을 제품 품질 자료로 보관한다.

## 15. 운영 범위와 결정 시점

초기에는 온라인 공동 편집, 출판 마켓 자동 등록, ISBN 대행, DRM, 인쇄 주문, AI 표지 생성, 별도 출판 서버를 개발하지 않는다. 전문 출판 외 기술문서·교재·사업계획서는 Author의 기존 기능과 소규모 서식·구성 템플릿으로 검증한다. 새 전문 엔진은 반복되는 유료 수요와 기존 기능의 한계가 확인될 때 별도 계획으로 판단한다.

0단계 감사가 끝나면 **공통 Core 추출 목록, 첫 EPUB 지원 범위, 검증기 배포 방식, 독립 앱 공수**를 확정한다. 인쇄 PDF의 사양은 대상 인쇄소와 시험본을 정한 뒤 확정한다. 제품 가격과 번들 정책은 기능·품질·운영비를 확인한 뒤 결정한다.

## 결론

독립 Publishing은 기존 Author의 원고와 검증된 기능을 사용하되, 출판 프로젝트·조판·검사·배포 책임을 별도로 가진다. 첫 작업은 Core 이동이나 새 UI 제작이 아니라 **기준 도서로 현재 EPUB·PDF 출력을 감사하는 것**이다. 그 결과에 맞춰 필요한 기능만 분리하고 가변형 EPUB을 첫 출시 제품으로 완성한다.
