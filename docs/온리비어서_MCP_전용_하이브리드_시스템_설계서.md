# 온리비어서 MCP 전용 하이브리드 시스템 설계서

설계 버전 2.0 · 2026-11-19 · 검토용 · 구현 전

## 1. 목표와 확정 요구사항

MCP 클라이언트에서 온리비 계정을 한 번 연결한 뒤, 온리비 어서 웹·데스크톱 편집기를 실행하지 않아도 Google Drive 문서와 연결된 PC의 로컬 문서를 조회·검색·작성·수정한다. 계정 연결은 유지하지만 **계정 사용 가능 상태, 구독, 장치, 폴더, 읽기·쓰기 권한은 각 작업 시점에 새로 확인**한다.

MCP에서 사용하는 **작업장 폴더**와 **리소스 폴더**는 MCP 전용 설정이다. 웹과 데스크톱 편집기의 현재 작업장·리소스 폴더를 복사하거나 동기화하지 않는다. MCP 클라이언트에서 두 폴더를 각각 최초 등록하고, 이후에도 인증을 다시 연결하지 않고 수시로 변경·해제할 수 있다. 각 폴더는 Drive 또는 로컬 장치의 폴더일 수 있다.

이번 설계의 `리소스 폴더`는 서식 프로필·AI 템플릿 등 온리비 리소스를 뜻한다. 집필 근거 자료를 모아 읽는 `참조 폴더`는 별도 개념이며 이번 필수 범위에는 포함하지 않는다. 필요해지면 읽기 전용 폴더 역할로 확장한다.

### 비목표

- 웹·데스크톱 편집기의 폴더 설정 변경 또는 자동 동기화
- Drive와 로컬 간 자동 양방향 파일 동기화
- PC가 꺼진 상태에서 로컬 원문 접근
- 서버에 로컬 문서 본문을 기본 저장하거나 모든 문서를 하나의 물리 폴더로 이동
- 사용자가 철회한 연결, 만료된 구독, Google 갱신 권한 무효화까지 재인증 없이 우회

## 2. 현재 구현과 설계 차이

| 현재 구현 | 설계에서 필요한 변화 |
| --- | --- |
| `functions/api/mcp/index.js`: Drive용 원격 Streamable HTTP MCP가 존재 | 새로 만드는 대신 인증·폴더·권한 계약을 확장 |
| `functions/api/mcp/token.js`: 앱이 선택한 Drive 작업장·리소스 폴더 ID를 토큰 발급 때 저장 | MCP 전용 폴더 설정을 인증 정보에서 분리; 변경 시 토큰 재발급 불필요 |
| `plugins/onrivi-author/server/context.mjs`: 실행 중인 데스크톱 앱의 최신 폴더 정보를 요구 | 독립 로컬 에이전트가 MCP 전용 로컬 폴더 설정을 사용 |
| `plugins/onrivi-author/server/authorization.mjs`: 앱 라이선스 파일·실행 프로세스를 요구하고 검사 결과를 최대 60초 캐시 | 장치에 연결된 계정의 현재 권한을 호출마다 확인; 장치 인증은 별도 유지 |
| 원격 MCP는 개인용 고정 Bearer 토큰 사용 | 지원 클라이언트에는 OAuth 기반 연결·갱신 제공; 기존 토큰은 이행 기간에 한정 |
| 원격 `replace_markdown`의 해시는 선택 사항 | 기존 문서 수정의 기준 버전 필수, 모든 쓰기의 폴더 설정 버전과 권한은 저장 직전 검증 |
| Drive 검색은 작업장 루트의 파일명 중심 | 재귀 목록·검색과 본문/RAG 검색 범위를 별도로 정의 |

기존 원격 MCP와 로컬 stdio MCP는 이행 기간에 보존한다. 전체 저장소 구조를 한 번에 재편하지 않는다.

## 3. 사용자 경험과 불변 조건

1. 사용자는 MCP 클라이언트에서 온리비 계정을 연결한다. 인증 정보가 유효하면 다음 사용 시 별도 로그인 없이 자동 갱신한다.
2. MCP에서 작업장·리소스 폴더를 각각 선택한다. 초기값은 **미설정**이며 편집기의 폴더를 자동 채택하지 않는다.
3. 클라이언트에서 `현재 폴더 조회`, `폴더 선택`, `폴더 변경`, `연결 해제`를 수행한다. 변경은 다음 도구 호출부터 적용한다.
4. 문서 목록·읽기·검색·쓰기 요청마다 현재 계정 상태와 요청한 작업의 권한을 검증한다.
5. 폴더 변경이나 권한 철회와 동시에 진행 중인 쓰기는 새 설정을 조용히 따라가지 않고 충돌로 중단한다.
6. 응답에는 실제 저장소 종류, 대상 장치 연결 상태, 폴더 역할, 문서 버전을 알려준다. 원격 응답에 불필요한 로컬 절대경로는 내보내지 않는다.
7. 에디터에서 같은 실제 폴더를 열더라도 두 설정은 독립적으로 유지한다. 파일 자체는 동일하므로 충돌 검사는 공통으로 적용한다.

## 4. 전체 구조

```text
MCP 클라이언트 (ChatGPT / Claude / OpenCode 등)
    │ Streamable HTTP + 사용자별 MCP 연결 인증
    ▼
Onrivi MCP Gateway (기존 /api/mcp 확장)
    ├─ 계정·구독·연결·폴더 권한 검사
    ├─ MCP 전용 설정 저장소 및 감사 기록
    ├─ Drive Adapter ── Google Drive API
    └─ Local Router ── 인증된 아웃바운드 연결 ── Local Agent
                                                   └─ 허용된 로컬 폴더
```

Gateway는 접근 제어와 도구 라우팅을 담당한다. Drive Adapter와 Local Agent는 같은 문서 인터페이스를 구현하되 저장소별 제약을 응답에 드러낸다. 편집기는 별도로 동작하며 MCP 설정의 공급원이 아니다. 기존 로컬 stdio MCP는 전환 기간의 호환 경로다. 단일 원격 MCP 연결에서 로컬까지 쓰려면 PC가 켜지고 Agent가 연결돼 있어야 한다.

### 4.1 배포 판단

현재 Drive 원격 MCP는 Cloudflare Functions 기반으로 존재한다. Drive만 다루는 단계에서 별도 상시 Node 서버를 전제로 하지 않는다. 로컬 Agent에 작업을 실시간 전달하려면 WebSocket, 장기 폴링, 메시지 큐 중 운영 환경에 맞는 전달 수단을 검증한다. **연결 방식과 운영비를 측정한 뒤** 별도 상시 서비스를 둘지 결정한다. 인증·폴더·문서 도구의 논리 계약은 어느 배포 방식을 선택해도 동일하게 유지한다.

## 5. 계정 연결, 자동 갱신, 실시간 사용 자격

인증은 서로 다른 세 층이다.

| 층 | 목적 | 유지·갱신 방식 |
| --- | --- | --- |
| MCP 클라이언트 ↔ 온리비 | 사용자와 클라이언트 연결 식별 | 지원 클라이언트는 OAuth 승인·짧은 접근 토큰·회전 가능한 갱신 토큰; 다른 클라이언트는 제한된 호환 방식 검토 |
| 온리비 ↔ Google | 사용자가 승인한 Drive 파일 접근 | Google 갱신 토큰으로 접근 토큰 자동 갱신; Google 권한 철회 시 재연결 필요 |
| Local Agent ↔ 온리비 | 등록된 PC 식별 | 장치별 자격 증명 보관·회전; 장치 해제 시 즉시 폐기 |

OAuth 기반 자동 갱신은 클라이언트의 지원 여부에 따른다. MCP 연결 토큰이 갱신돼도 계정·구독·폴더 권한이 보장되는 것은 아니다. 사용자에게 매번 로그인 창을 띄우지 않되, **각 도구 호출의 서버 측 권한 조회**는 계속 수행한다.

### 5.1 도구 호출별 인가 절차

```text
인증 정보 확인
→ 연결·계정·장치의 현재 활성 상태 조회
→ 현재 구독 및 MCP 사용 자격 조회
→ 현재 MCP 전용 폴더 설정과 설정 버전 조회
→ 도구별 읽기/쓰기 권한과 대상 폴더 범위 검사
→ 저장소에서 실행
→ 쓰기 직전 권한·폴더 버전·문서 버전 재검증
→ 결과와 감사 기록
```

계정 상태와 구독 상태는 호출마다 권위 있는 저장소에서 조회한다. 로컬 Agent는 Gateway가 발급한 짧은 수명의 작업 지시를 받더라도, 경로와 허용 폴더는 Agent에서 다시 검증한다. 권한 변경 알림은 빠른 취소를 돕는 보조 수단이며, 인가 판단의 유일한 근거로 사용하지 않는다. 권한 조회가 실패하면 쓰기는 수행하지 않는다. 읽기도 실시간 권한을 확인할 수 없다면 수행하지 않는 정책을 기본으로 한다.

`tools/list` 같은 메타데이터 응답과 실제 `tools/call`의 인가 정책은 분리한다. 도구 목록이 보여도 각 실행은 반드시 현재 권한으로 검사한다.

## 6. MCP 전용 폴더 설정

### 6.1 설정 단위

설정은 `사용자 계정 + MCP 연결`에 속한다. 한 계정이 여러 MCP 클라이언트를 연결하면 각각 다른 작업장·리소스 폴더를 지정할 수 있다. 동일 클라이언트의 여러 연결도 고유 연결 ID로 구별한다. 사용자 계정은 연결 목록, 마지막 사용 시각, 장치, 폴더 및 권한을 조회·해제할 수 있다.

각 연결의 작업장과 리소스는 별도 슬롯이다. 빈 값은 허용하며, 빈 작업장에 대한 문서 도구와 빈 리소스 폴더에 대한 템플릿·서식 도구는 명확한 설정 필요 응답을 반환한다. **편집기 폴더로 자동 폴백하지 않는다.**

### 6.2 폴더 설정 모델

| 필드 | 의미 |
| --- | --- |
| `connectionId` | MCP 연결 식별자 |
| `role` | 작업장 또는 리소스 폴더 역할 |
| `storageType` | Drive 또는 로컬 |
| `driveAccountId`, `folderId` | Drive 계정과 폴더 식별자 |
| `deviceId`, `rootId` | 로컬 장치와 Agent가 발급한 허용 폴더 식별자 |
| `permissions` | 읽기, 쓰기 등 명시적으로 허용한 동작 |
| `configVersion` | 폴더 설정이 바뀔 때마다 증가하는 버전 |
| `availability` | Drive 접근 가능 또는 로컬 Agent 온라인·오프라인 상태 |
| `updatedAt` | 마지막 변경 시각 |

Drive 폴더의 이름이나 로컬 폴더의 표시 이름은 UI용이며 권한 판단에 쓰지 않는다. 로컬 절대경로는 Agent가 보관하고 Gateway에는 `rootId`와 제한된 표시 정보만 저장한다. 폴더가 이동·삭제되거나 Drive 권한이 철회되면 임의 폴백 없이 해당 슬롯을 사용 불가로 표시한다.

### 6.3 등록과 변경

클라이언트는 후보 폴더를 조회하거나 사용자가 선택한 식별자를 제출한다. Gateway는 현재 사용자·Drive 계정 또는 장치 연결을 확인한다. 로컬 Agent는 사용자의 해당 장치에서 폴더 선택·허용을 확인하고 실제 경로를 검증한다. Drive는 계정의 접근 가능 여부와 허용 범위를 확인한다. 성공 시 버전을 올려 지속 저장한다.

폴더 변경에는 조회한 `expectedConfigVersion`을 요구한다. 두 클라이언트가 동시에 설정을 바꾼 경우 후발 요청은 충돌로 중단한다. 변경 후 새 호출은 새 폴더를 사용한다. 이미 시작한 쓰기는 최초 설정 버전과 저장 직전 버전이 다르면 중단한다. 폴더 변경은 기존 폴더의 파일을 이동·복사하거나 편집기의 폴더를 바꾸지 않는다.

로컬에서 폴더 선택을 처음 승인하거나 새 폴더로 변경할 때는 해당 PC에서 사용자 확인이 필요할 수 있다. **이미 승인된 폴더 사이의 전환**은 저장된 권한 안에서 MCP 클라이언트가 수행할 수 있다. 웹 브라우저나 원격 클라이언트가 임의의 Windows 절대경로만 보내서 새 로컬 폴더를 허용하도록 만들지 않는다.

## 7. 문서 식별과 저장소 어댑터

외부에 노출되는 식별자는 예를 들어 `onrivi://drive/{accountId}/{fileId}` 또는 `onrivi://local/{deviceId}/{rootId}/{opaqueDocumentId}` 형식으로 설계한다. 로컬 파일 이름·이동에 따라 식별자가 달라지지 않게 Agent가 경로 매핑을 관리한다. 단, 이동 추적의 정확도는 파일 시스템 특성에 좌우되므로 원본 파일 식별과 이름 변경 규칙을 별도로 검증한다.

```text
list(folder, cursor)
read(documentId) -> content + revision + storage metadata
create(folder, name, content, expectedConfigVersion)
replace(documentId, content, expectedRevision, expectedConfigVersion)
editSection(documentId, target, replacement, expectedRevision, expectedConfigVersion)
search(query, scope, cursor)
```

두 어댑터는 같은 응답 구조를 사용한다. `storageType`, `deviceId`(로컬일 때), `availability`, `revision`, `modifiedAt`, `permissions`를 포함한다. Drive와 로컬에 같은 이름의 파일이 있어도 서로 다른 문서다. 명시적 복사 기능 없이는 자동으로 합치지 않는다.

## 8. MCP 도구 계약

도구명은 기존 클라이언트 호환성을 위해 가능한 한 현재 이름을 유지한다. 아래의 새 이름은 **설계 제안**이며 실제 시스템 공통코드나 확정 API가 아니다.

| 분류 | 도구 | 동작 |
| --- | --- | --- |
| 계정·연결 | `get_mcp_connection_status` | 현재 계정·구독·연결·장치 상태와 가능한 동작 조회 |
| 폴더 | `get_mcp_folders` | 이 MCP 연결의 현재 작업장·리소스·버전 조회 |
| 폴더 | `list_mcp_folder_candidates` | 선택 가능한 Drive·로컬 폴더 목록 조회; 로컬은 Agent 온라인 필요 |
| 폴더 | `set_mcp_workspace` | 작업장 등록·변경; 변경할 설정 버전 필수 |
| 폴더 | `set_mcp_resource_folder` | 리소스 폴더 등록·변경; 변경할 설정 버전 필수 |
| 폴더 | `clear_mcp_folder` | 지정 슬롯 해제 |
| 문서 | 기존 `list_workspace_files`, `read_markdown`, `create_markdown`, `replace_markdown`, `edit_markdown_section` | 현재 MCP 작업장에만 적용 |
| 검색 | 기존 `search_workspace` | 검색 범위와 본문 검색 지원 범위를 응답에 명시 |
| 리소스 | 기존 템플릿·서식 도구 | 현재 MCP 리소스 폴더에만 적용 |
| 장치 | `get_mcp_device_status` | 선택된 로컬 장치의 연결 상태 조회 |

문서 도구는 기본적으로 현재 연결의 작업장을 대상으로 한다. 리소스 폴더 내 파일 접근은 템플릿·서식 도구처럼 목적이 명확한 도구로 제한한다. 특정 문서를 식별자로 직접 지정할 때도 현재 연결의 허용된 폴더 안에 있는지 검증한다. 읽기·쓰기 권한을 별개로 검사한다. 도구 인자에 임의의 폴더 ID나 경로가 들어와도 해당 값만 믿고 접근하지 않는다.

## 9. Google Drive 처리

사용자는 MCP 연결에 사용할 Drive 계정을 승인한다. 작업장과 리소스 폴더는 그 계정에서 별도로 선택한다. Google OAuth의 갱신 토큰은 서버에서 암호화 보관하고 접근 토큰을 자동 갱신한다. Drive 권한 범위는 실제 폴더 탐색·기존 파일 접근·생성 요구를 기준으로 재검토한다. 현재 사용 중인 전체 `drive` 범위에서 `drive.file` 등으로 줄일 수 있는지는 실제 사용 흐름으로 확인해야 한다.

Drive 파일 ID로 직접 접근하는 모든 경로에서 현재 폴더의 자손인지, 현재 계정으로 접근 가능한지, 파일 유형이 허용되는지 검사한다. 공유 드라이브, 바로가기, 여러 부모와 이름 중복, 페이지네이션을 포함해 검증한다. 단순히 `fileId`를 소유하고 있다는 이유로 MCP 작업장 외부 접근을 허용하지 않는다.

Drive 문서 수정은 기준 revision을 필수로 요구한다. 수정 직전 조회만으로 동시 수정 경쟁을 완전히 없앨 수 없으므로 Drive API가 지원하는 조건부 갱신 방식을 확인해 사용한다. 불가능한 경우에는 해당 한계를 문서화하고 직렬화 또는 잠금 정책을 별도로 둔다.

## 10. Local Agent 처리

Agent는 Windows 사용자 권한으로 독립 실행하며, 편집기가 종료돼도 PC가 켜져 있으면 연결을 유지한다. 장치 등록, 자동 시작, 일시정지, 종료, 폴더 허용·해제, 재연결 상태를 제공한다. 클라우드에서 PC로 직접 인바운드 연결하지 않고 Agent가 인증된 아웃바운드 연결을 맺는다.

로컬 폴더 설정의 실제 경로와 접근 권한은 Agent의 보호된 저장소에 둔다. 매 요청에 사용자·장치·연결·폴더 역할·작업 권한·설정 버전을 확인하고, `realpath`로 허용 폴더 이탈과 심볼릭 링크·정션 경유를 검사한다. 파일 열기와 교체 직전에도 대상이 같은 허용 경계 안에 있는지 검증한다. 문서 내용은 요청 처리에 필요한 동안만 전달하며 기본적으로 서버 DB에 색인하거나 저장하지 않는다.

PC 또는 Agent가 오프라인이면 로컬 요청은 짧은 제한 시간 안에 상태를 반환한다. 쓰기 요청은 자동 예약하지 않는다. Agent가 뒤늦게 연결돼도 오래된 수정 명령을 실행하지 않는다. PC에서 직접 실행되는 기존 stdio MCP는 초기 마이그레이션 동안 유지하되, 독립 Agent·MCP 전용 설정으로 전환한 뒤 기능 중복을 정리한다.

## 11. 검색과 RAG의 관계

`list`는 목록, `search_workspace`는 문서 찾기, RAG는 관련 근거 청크 찾기다. 세 동작을 같은 이름으로 섞지 않는다. Drive 검색이 파일명만 지원하면 그 사실을 응답에 표시한다. 본문 검색을 제공하려면 Drive 파일의 내용 색인 정책, 변경 감지, 권한 철회 시 색인 제거를 먼저 정의한다.

기존 온리비 지식 보관함의 SQLite 색인은 그대로 별도 영역으로 둔다. 이 설계가 SQLite를 PostgreSQL로 대체하지 않는다. 원격 MCP에서 로컬 문서를 RAG 검색하게 하려면 PC가 온라인일 때 Agent가 검색을 수행하거나, 사용자가 별도로 승인한 색인 동기화가 필요하다. `서버에 로컬 문서 본문을 기본 저장하지 않음` 정책 아래에서 PC가 꺼진 상태의 로컬 본문 검색을 약속하지 않는다.

## 12. 동시 수정과 데이터 무결성

모든 쓰기는 `expectedConfigVersion`을 받고, 기존 문서의 전체·부분 수정은 `expectedRevision`도 받는다. 새 문서 생성은 대상 이름이 존재하지 않는지 원자적으로 검증한다. `expectedRevision`은 읽은 문서의 SHA-256 또는 저장소가 보장하는 조건부 revision이다. 부분 수정은 전체 문서 재작성보다 대상 제목·기존 문구의 정확한 일치와 현재 문서 버전을 확인한다. 결과에는 새 revision을 반환한다.

저장 전 검증: 계정·구독 → 연결·장치 → 폴더 설정 버전 → 읽기/쓰기 권한 → 대상이 폴더 경계 안인지 → 문서 revision. 로컬은 임시 파일과 원자적 교체를 사용하되 같은 파일을 다른 프로세스가 수정하는 경쟁을 검증한다. Drive는 API 조건부 갱신을 확인한다. 어느 검증이든 실패하면 저장하지 않는다.

폴더 변경은 파일 쓰기와 별도 설정 트랜잭션이다. 폴더 변경으로 진행 중인 작업을 새 폴더에 재대상화하지 않는다. Drive와 로컬의 동명 파일은 별개이며 자동 동기화나 암묵적 복사는 하지 않는다.

## 13. 설정 저장과 운영 데이터

계정·연결·폴더 권한·장치·설정 버전·감사 메타데이터는 서버의 계정 관리용 저장소에서 관리한다. 기존 PostgreSQL 계정·구독 조회를 재사용할 수 있다. 토큰과 Google 갱신 정보는 별도의 암호화된 비밀 저장소에 보관하고 로그에 기록하지 않는다. 로컬 실제 경로와 장치 자격 증명은 Agent 측 보호 저장소에 둔다. **문서 원문과 기존 SQLite 지식 색인은 이 메타데이터 저장소로 옮기지 않는다.**

연결별 한 개의 설정 문서로 시작할 수도 있지만, 여러 클라이언트·장치의 동시 변경과 즉시 철회가 필요하므로 버전 있는 원자적 갱신과 권위 있는 조회가 가능한 저장소를 선택한다. 현재 R2의 사용자별 단일 MCP 토큰 레코드는 다중 연결과 독립적인 폴더 변경을 위한 최종 데이터 모델로 사용하지 않는다.

## 14. 권한·보안·오류 정책

- MCP 인증 정보는 연결별로 분리하고 분실·철회 시 해당 연결만 폐기한다.
- 연결 승인과 폴더 설정 변경은 현재 계정 자격을 확인한다. 새 로컬 폴더의 최초 허용은 해당 PC 사용자 확인을 요구한다.
- 원격 MCP는 현재 지정된 작업장·리소스 폴더 외의 Drive 파일을 ID로 직접 읽거나 쓸 수 없어야 한다.
- 읽기와 쓰기를 분리하고, 목록·검색 결과도 동일한 폴더 경계를 적용한다.
- 저장소 오프라인, 계정 사용 불가, 권한 철회, 폴더 변경, 문서 충돌을 서로 구분해 응답한다.
- 로컬 절대경로, Google 토큰, 장치 비밀, 문서 본문을 감사 로그에 남기지 않는다.
- 계정 연결 해제·폴더 해제·장치 해제는 다음 요청부터 효력을 갖고, 진행 중 쓰기는 저장 직전 재검증으로 중단한다.
- 요청 크기, 응답 크기, 시간 제한, 호출량 제한과 감사 기록은 저장소별로 설정한다.

신규 오류 코드나 상태 코드가 실제 구현에 필요해지면 프로젝트의 공통코드 승인 절차를 거쳐 확정한다. 이 문서의 명칭은 설계 설명이며 등록된 공통코드가 아니다.

## 15. 단계별 개발 순서와 완료 기준

### 단계 0 — 현재 원격 MCP의 경계 보강

Drive 파일·폴더 ID가 MCP 작업장 밖을 가리켜도 접근하지 못하게 하고, 기존 문서 수정의 기준 버전을 필수화한다. 기존 토큰 방식과 도구의 실제 동작을 통합 테스트로 확인한다.

### 단계 1 — MCP 전용 연결·폴더 설정

사용자별·연결별 작업장과 리소스 폴더를 독립 저장한다. MCP 도구에서 폴더를 조회·등록·수정·해제한다. 앱의 폴더 설정을 변경하거나 자동 복사하지 않는 것을 검증한다. 두 클라이언트가 다른 폴더를 사용하고, 변경 직후 다음 요청에 반영되는 것을 확인한다.

### 단계 2 — 계정 연결과 작업별 실시간 인가

지원 클라이언트의 OAuth 자동 갱신을 검증하고, 현재 구독·계정·연결 상태를 매 도구 호출에서 조회한다. 권한·폴더를 변경한 뒤 이전 권한으로 읽기나 쓰기를 시도했을 때 거부되는 것을 확인한다. 기존 고정 토큰의 전환 경로를 제공한다.

### 단계 3 — Drive 문서 완성

MCP 전용 Drive 작업장·리소스 폴더에서 목록·읽기·검색·생성·수정·템플릿·서식 도구를 검증한다. 재귀 검색, 페이지네이션, 범위 제한, 공유 폴더, 이름 중복, 수정 충돌을 검증한다.

### 단계 4 — 독립 Local Agent

편집기가 종료된 상태에서 등록된 PC가 켜져 있으면 MCP로 로컬 문서를 읽고 수정할 수 있어야 한다. 새 폴더는 PC 사용자가 허용하고, Agent 오프라인·권한 철회·경로 이탈·폴더 변경·문서 충돌에서 안전하게 중단해야 한다.

### 단계 5 — 단일 연결 통합 검증

하나의 MCP 연결에서 Drive와 로컬 작업장·리소스 조합을 바꿔 사용한다. ChatGPT·Claude·OpenCode의 실제 지원 인증·전송 방식은 각각 검증한다. 지원하지 않는 클라이언트에는 해당 기능의 제한을 명시한다. 운영비와 장애 복구 시간을 측정한다.

## 16. 검증 시나리오

1. 계정을 한 번 연결한 뒤 토큰이 갱신돼도 로그인 창 없이 계속 사용한다. 그 사이 구독을 중단하면 다음 도구 호출이 거부된다.
2. 같은 사용자 A·B 두 MCP 연결이 각각 다른 작업장을 사용한다. A의 폴더 변경이 B 또는 웹·데스크톱 편집기의 폴더를 바꾸지 않는다.
3. 작업장을 Drive, 리소스를 로컬로 설정하고 각 도구가 지정된 저장소만 사용한다.
4. 작업장 변경 후 이미 시작한 쓰기는 설정 버전 불일치로 중단된다.
5. Drive 폴더 밖의 유효한 파일 ID·폴더 ID를 제출해도 목록·읽기·쓰기 모두 거부된다.
6. 로컬 에이전트를 종료하면 로컬 요청은 오프라인으로 끝나고, Drive 요청은 계속 작동한다. 재연결해도 과거 쓰기 요청은 실행되지 않는다.
7. 다른 프로그램이 문서를 수정하면 예전 revision의 전체·부분 수정 요청이 거부된다.
8. 폴더 권한을 읽기 전용으로 변경하면 읽기는 가능하고 신규 작성·수정은 즉시 거부된다.
9. Google 권한을 철회하면 Drive 도구는 재연결을 요구하고 로컬 도구는 별도 연결 상태에 따라 동작한다.
10. 설정되지 않은 폴더를 임의의 편집기 폴더나 기본 경로로 대체하지 않는다.

## 결론

기존 Drive 원격 MCP를 기반으로, **MCP 연결별 전용 작업장·리소스 폴더**와 **호출마다 최신 계정·권한 검사**를 먼저 확립한다. 이후 앱과 독립적인 Local Agent를 붙이면 하나의 MCP 연결에서 Drive와 로컬 폴더를 선택해 사용할 수 있다. 인증 자동 갱신은 반복 로그인을 줄이는 기능이며, 사용 자격과 폴더 권한의 실시간 검사를 대신하지 않는다.
